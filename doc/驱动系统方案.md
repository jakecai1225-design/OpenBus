# openbus 驱动插件系统方案

> **状态：阶段 1–4 已实施（2026-08-18）；v2 演进方案（§十三：统一插件市场 + 官方设备收敛）已实施（2026-08-18）；v2.2 第一批扩容（slcan + candle，§14.7）代码已落地（2026-08-18，GUI 冒烟通过，真机验收待样机）**
>
> 目标：将采集硬件驱动从主程序静态编译改为**可从官方设备市场下载安装的驱动插件包**，
> 与现有 Python 插件（`.opk`，宿主进程运行）不同，驱动插件是**原生代码，加载运行在主进程内**，
> 以最低时延对接各厂家 USB-CAN / CAN FD 采集设备。
>
> **v1 动线（已被 v2 取代）**：设备连接折叠栏「＋ 新增设备」→「新增设备」标签页
>（设备市场：搜索 / 图文详情 / 一键安装）→ 驱动热加载后设备折叠栏即现该厂商分区。
>
> **v2 动线（已实施）**：设备折叠栏原生仅 openbus 官方设备（openbus 模拟器）与「＋ 新增设备」→
> 自动跳转统一「插件市场」标签页（VS Code 风格：驱动 + 工具插件同场搜索/安装/卸载）→
> 安装后设备树即现厂商分区（详见 §13）。

## 一、README 中采集硬件相关内容提取

> 本节内容提取自 `README.md`，作为方案的需求与现状依据。

### 1.1 设备抽象层 HAL（README「整体架构设计」）

- 分层：UI 交互层 → 业务服务层 → 核心数据内核层 DataCore → **设备抽象层 HAL（对标 CANoe VTI）**
- HAL 三类实现：**硬件采集适配器**（对接采集器 USB 数据流，接收带硬件时间戳的 CAN/CAN FD/EtherCAT 原始报文）、**离线文件适配器**（BLF/ASC/自定义录制）、**仿真源适配器**
- 统一抽象接口 `IBusSource`：开启/关闭通道、报文接收回调、发送报文接口
- 输出标准统一报文结构体 `BusMessage`（统一纳秒时间戳 / bus_type / channel / id / data / is_error_frame）

### 1.2 其他硬件相关库（README「其他硬件相关库」）

| 功能 | 推荐方案 | 备注 |
|------|---------|------|
| SocketCAN (Linux) | libsocketcan (MIT) | Linux 原生支持 |
| Kvaser USB 设备 | Kvaser C API SDK（商用） | 需购买授权，Windows/Linux/macOS |
| PEAK-Systems PCAN | PEAK SDK（PCAN-Basic 免费） | Windows/Linux |
| BLF/ASC/CSV/PCAP/TRC 日志 | 自研解析 | ✅ 已实现 |

集成顺序建议：内置模拟器完成逻辑开发 → 优先 Kvaser → 按需补充 SocketCAN / PEAK。

### 1.3 硬件接入规划（README「硬件接入规划」章节）

- 接入 **ZLG、PEAK、开源 USB-CAN** 三大类设备；不存在现成库统一覆盖多家，需**自建抽象层 + 分厂商封装**
- 在 `CanSimulator` / `Player` / `Recorder` 管线中插入 `ICanDevice` 抽象层：

```
ICanDevice (src/core/candevice.h)
├── CanDeviceZLG        — 动态加载 zlgcan.dll，封装全部原生 API
├── CanDevicePeak       — 封装 PCAN-Basic 库
├── CanDeviceCandleLight — libusb + GS_USB 协议（推荐的开源设备路径）
└── CanDeviceSlcan     — 串口文本协议（兼容老旧开源硬件）
```

- 通用帧收发走虚基类 `Open/Send/Recv`；厂商特有功能（硬件时间戳、滤波、错误帧、ISO 切换）通过 `VendorCtrl(cmd, args)` 扩展，不阉割能力
- 工厂模式枚举设备（ZLG `ZCAN_FindDevice` / PCAN `CAN_GetValue` / libusb 扫 VID:PID），动态创建实例
- DLL 缺失时优雅降级（`LoadLibrary` + 友好提示），不影响其他后端

**厂商 SDK 矩阵：**

| 厂商 | 库 | 能力 | 授权 |
|------|----|------|------|
| ZLG | `zlgcan.dll` / `libzlgcan.so` | CAN/FD、硬件滤波、总线负载、错误帧、硬件时间戳 | 商用 SDK，Linux 端仅预编译 so |
| PEAK | PCAN-Basic | CAN/FD/XL、ISO 切换、硬件时间戳、通道状态 | 免费，商用分发需保留版权声明 |
| 开源（推荐） | CandleLight / GS_USB | CAN FD、硬件时间戳、USB 高速 | MIT（固件 + 协议栈） |
| 开源（兼容） | SLCAN | 串口文本协议，**无硬件时间戳** | 开放规范 |

**风险提示（README 原文归纳）：**
1. ZLG Linux 端无开源，仅预编译 `libzlgcan.so`
2. SLCAN 无硬件时间戳，界面需区分「硬件时间戳」与「软件接收时间」
3. 厂商 DLL 必须动态加载，避免缺失 DLL 导致程序崩溃
4. PCAN-Basic 商用分发需保留版权声明

**UI 交互约定：** 侧边栏「设备连接」显示设备系列树（不显示参数），点击跳转「设备连接」标签页完成全部参数配置（通道、波特率、CAN FD、高级时序），以支持不同设备类型的参数差异；设备树折叠栏底部提供「＋ 新增设备」入口，打开「新增设备」标签页从设备市场搜索/安装驱动（见 §8.4）。

**README 实现状态：** `ICanDevice` / `CanDeviceZLG` / `CanDeviceManager` / `DevicePanel` / `DeviceConnectionTab` ✅ 已实现；`CanDevicePeak`、`CanDeviceCandleLight`、`CanDeviceSlcan` 当时待实现（现 PEAK/Kvaser 已补齐，见下节现状）。

### 2.2 核心问题

1. **后端静态编译进主程序**：新增一家厂商 = 修改 `candevice.cpp` 工厂 + 重编译 + 重新发布整个应用；
2. **品牌枚举封闭**：`ICanDevice::Brand` 是编译期枚举（ZLG=0…SLCAN=4），第三方/长尾厂商无法在不改主程序的情况下接入；
3. **主程序体积与授权耦合**：所有厂商封装代码（含 SDK 头文件依赖）都进主程序，即使用户只用一家设备；
4. **分发粒度粗**：用户需要的是「按需安装我手上这台设备的驱动」，而不是「等官方发新版」。

### 2.3 需求（本方案要解决的）

| # | 需求 | 来源 |
|---|------|------|
| R1 | 尽可能多地适配不同厂家、不同类型的采集设备 | 用户 |
| R2 | 驱动以**插件包**形式从**官方应用市场**下载安装（复用插件市场的分发思路） | 用户 |
| R3 | 与 Python 插件不同，驱动插件**安装运行到主进程中**（原生、进程内、低时延） | 用户 |
| R4 | 保留现有 `ICanDevice` 抽象与 `CanDeviceManager` 管线（时间戳归一化、滤波、接收线程模型不变） | 现状约束 |
| R5 | 厂商 DLL 缺失/驱动不兼容时优雅降级，不影响其他驱动与主程序 | README 风险提示 |
| R6 | 驱动安装后**无需重启**即可使用（热加载） | 体验目标 |
| R7 | 新增设备体验流：设备连接折叠栏「＋ 新增设备」→「新增设备」标签页，按**型号**搜索、看图文详情选型，一键安装后折叠栏即现设备 | 用户 |

## 三、方案选型

「主进程内运行动态驱动」有四种技术路径，对比如下：

| 维度 | A. Qt 原生插件（QPluginLoader） | B. 纯 C ABI 函数表 | C. 独立驱动进程 + IPC | D. 嵌入脚本（Python in-proc） |
|------|------|------|------|------|
| 运行位置 | **主进程内** | 主进程内 | 进程外 | 主进程内（解释器） |
| 收发时延 | 零拷贝，与内置后端一致 | 零拷贝 | IPC 序列化开销，微秒级抖动 | GIL 阻塞接收线程，高负载丢帧 |
| 接口表达力 | C++ 虚接口 + Qt 类型，与 `ICanDevice` 天然衔接 | 样板多，对象生命周期手工管理 | 可复用 Python 宿主消息协议 | 需 ctypes 绑定原生 SDK，反而低效 |
| ABI 稳定性 | 要求同 Qt 版本 + 同编译器（见 3.2） | 跨编译器稳定 | 最松 | 依赖解释器版本 |
| 崩溃隔离 | 无（同进程） | 无 | **有** | 无 |
| Qt 生态惯例 | ✅ Qt 自身 imageformat / platform 插件即此机制 | — | — | — |
| 与 R3 匹配 | ✅ | ✅ | ❌（用户明确要求进程内） | 部分 |

**结论：选 A —— QPluginLoader 原生插件机制**，辅以 B 的思想做接口版本化（IID 带版本号）。

- 驱动 = 一个用与主程序**相同工具链**构建的 Qt 插件 DLL，实现 `CanDriverPlugin` 接口；
- 官方市场统一构建分发，规避跨编译器 ABI 问题；
- C 路线（进程外）作为**逃生通道保留**：接口抽象后，未来可为高风险驱动加 out-of-proc 适配器（v1 不做）。

### 3.2 ABI 兼容契约（驱动构建要求）

| 项 | 约束 |
|----|------|
| Qt 版本 | 与主程序同大版本（Qt 6.8.x） |
| 编译器 | MinGW-w64 13.1（GCC 13，`-std=c++17`），x86_64 |
| 跨 DLL 边界类型 | 仅 Qt 值类型（QString/QList…）、POD 结构、`ICanDevice*` 裸指针；**不跨界传 STL 容器**（MinGW STL 无稳定 ABI 承诺），现有 `ICanDevice` 已用 `std::vector`，接口内联保留但文档标注为契约一部分 |
| 接口演进 | 只增不改：新增虚函数只能追加在末尾并升 IID 版本（`/2.0`）；修改既有签名 = 破坏性变更，禁止 |
| 元数据预检 | 加载前经 `QPluginLoader::metaData()` 校验 `abiVersion` / `minAppVersion` / 架构，不满足直接拒绝，不进入 `load()` |

## 四、总体架构

```
┌────────────────────────── 官方应用市场 ──────────────────────────┐
│  market.json 索引（静态托管即可）                                  │
│  [{ id, name, vendor, version, url, sha256, minAppVersion, ... }]│
└───────────────┬──────────────────────────────┬───────────────────┘
                │ 下载 .odp                     │ 浏览/搜索（「新增设备」标签页 = 设备市场，§8.4）
                ▼                               ▼
        ┌─────────────── 阶段4：DriverInstaller（主程序内） ───────────────┐
        │ 校验 sha256（→ 阶段4 Ed25519 验签）→ 安装确认弹窗 → 解压到 drivers/ │
        └───────────────────────────────┬───────────────────────────────┘
                                        ▼
                          drivers/<driverId>/  （安装目录）
                          ├── driver.json      清单（含 CHECKSUMS 校验过的文件表）
                          ├── driver_<id>.dll  Qt 插件（原生驱动）
                          ├── vendor/          厂商运行时 DLL + LICENSE
                          └── icon.svg
                                        │
                                        ▼  扫描 / 热加载 / 卸载
        ┌────────────────── DriverRegistry（新增，主进程单例） ──────────────┐
        │ • 启动扫描 drivers/，metaData 预检（abi/arch/版本）后 QPluginLoader │
        │ • 对外：drivers() 元数据列表 / enumerateDevices() / createDevice()   │
        │ • 内置后端（ZLG/PEAK/Kvaser）注册为「内置驱动」，与外置统一视图      │
        └───────┬───────────────────────────────────────────┬───────────────┘
                │ createDevice(subType)                      │ 元数据（设备树）
                ▼                                           ▼
        ICanDevice 实例（driver dll 内）              DevicePanel / DeviceConnectionTab
                │                                           （动态生成，不再硬编码品牌）
                ▼
        CanDeviceManager（不变：接收线程 + FrameQueue + 时间戳归一化）
                │ frameGenerated
                ▼
        MainWindow → Trace / Graphic / Recorder / 插件 ……
```

要点：

1. **DriverRegistry 是唯一装配点**：`ICanDevice::create()` / `enumerateAll()` 改为委托 Registry；UI 设备树由 Registry 元数据驱动。
2. **内置驱动保底**：现有三个静态后端包装成「内置驱动条目」注册进 Registry（driverId 固定），保证零驱动安装时 ZLG/PEAK/Kvaser 开箱可用；外置驱动同 id 时**版本高者优先**并可覆盖内置。
3. **管线不变**：`CanDeviceManager`、时间戳归一化、硬件滤波、接收线程模型完全复用，驱动插件只替换「设备实例从哪来」。
4. **热加载**：QPluginLoader 支持运行期 load，安装成功后立即注册并刷新设备树，无需重启（R6）。
5. **市场以设备为中心**：市场条目按「设备型号」组织（图文详情/能力标签/规格表），条目关联驱动包；安装后该厂商分区即时出现在设备折叠栏（R7，详见 §8.4）。

## 五、驱动接口设计

### 5.1 插件级接口（新增 `src/core/driver/candriverplugin.h`）

```cpp
#ifndef CANDRIVERPLUGIN_H
#define CANDRIVERPLUGIN_H

#include "core/candevice.h"
#include <QString>
#include <QStringList>
#include <vector>

/**
 * @brief CAN 驱动插件接口 — 主进程内原生驱动（QPluginLoader 加载）
 *
 * 驱动包(.odp)安装到 drivers/<id>/ 后由 DriverRegistry 加载。
 * 实现方：QObject + 本接口 + Q_PLUGIN_METADATA（见 driver SDK 模板）。
 * ABI 契约：同 Qt 版本 + 同编译器（MinGW 13.1 x64, C++17），IID 版本化。
 */
class CanDriverPlugin
{
public:
    virtual ~CanDriverPlugin() = default;

    /// 驱动唯一标识（小写，如 "zlg" / "peak" / "candle" / "slcan"）
    virtual QString driverId() const = 0;

    /// 显示名（如 "ZLG 致远电子"）
    virtual QString displayName() const = 0;

    /// 驱动版本（与 driver.json 一致）
    virtual QString version() const = 0;

    /// 支持的设备子类型（与 driver.json devices[].type 对应）
    virtual QStringList deviceTypes() const = 0;

    /// 枚举当前可用物理设备（内部 QLibrary 加载厂商 DLL，失败返回空）
    virtual std::vector<ICanDevice::DeviceInfo> enumerateDevices() const = 0;

    /// 创建设备实例（返回裸指针，调用方 unique_ptr 接管生命周期）
    /// @param subType driver.json devices[].type
    virtual ICanDevice *createDevice(int subType) const = 0;
};

Q_DECLARE_INTERFACE(CanDriverPlugin, "com.sin.openbus.CanDriverPlugin/1.0")

#endif // CANDRIVERPLUGIN_H
```

### 5.2 驱动实现侧模板（驱动 SDK，随主程序源码 `drivers/template/` 提供）

```cpp
#include "candriverplugin.h"
#include <QObject>

class ZlgDriverPlugin : public QObject, public CanDriverPlugin
{
    Q_OBJECT
    Q_PLUGIN_METADATA(IID "com.sin.openbus.CanDriverPlugin/1.0" FILE "driver.json")
    Q_INTERFACES(CanDriverPlugin)

public:
    QString driverId() const override   { return QStringLiteral("zlg"); }
    QString displayName() const override{ return QStringLiteral("ZLG 致远电子"); }
    QString version() const override    { return QStringLiteral("1.0.0"); }
    QStringList deviceTypes() const override;
    std::vector<ICanDevice::DeviceInfo> enumerateDevices() const override; // 复用 CanDeviceZLG::enumerate()
    ICanDevice *createDevice(int subType) const override;                  // new CanDeviceZLG(subType)
};
```

- 现有 `CanDeviceZLG/PEAK/Kvaser` 类**代码平移**进各自驱动工程，几乎零改动；
- 厂商 DLL 由驱动内部 `QLibrary` 以**自身模块目录**为基准的绝对路径加载（见 7.3 隔离规则）。

### 5.3 与现有 `ICanDevice` 的关系

- `ICanDevice` 接口**不动**（open/close/send/recv/vendorCtrl/滤波已覆盖 README 全部能力要求）；
- `Brand` 枚举降级为「内置驱动兼容映射」：`DeviceKind`/`Brand` 继续工作，Registry 内部以 `driverId` 字符串为主键，`Brand` ↔ `driverId` 做静态映射（zlg/peak/kvaser/tongxing/slcan）；
- 新增长尾厂商只提供 `driverId` 字符串，不再需要改主程序枚举 —— 解决 2.2 问题②。

## 六、驱动包格式 `.odp`（openbus driver package）

### 6.1 包结构（ZIP）

```
zlg-driver_1.0.0_x64.odp
├── driver.json          # 清单（见 6.2）
├── driver_zlg.dll       # Qt 原生插件（MinGW 13.1 x64）
├── icon.svg             # 市场与详情页图标（扁平风格，同插件图标规范）

├── assets/              # 设备图片 + Markdown 详情（安装后离线展示/市场兜底）

└── vendor/              # 厂商运行时（可选，随包分发需注意授权）

```

字段说明：`devices[]` 驱动 UI 设备树与 `DeviceConnectionTab` 子类型下拉的**数据来源**（`image` 可选，指向包内 assets，供设备树/连接页缩略图）；`vendorSdk` 用于安装确认弹窗展示授权信息；`busType` 为 v2 泛化（LIN/EtherCAT）预留。市场详情页的完整图文（多图/规格/介绍）以 market.json 为准，包内 assets 为离线兜底（见 §8.1/§8.4）。

### 6.3 安装目录与打包工具

```
<应用根>/drivers/<id>/         ← 安装目标（项目已预留空 driver/ 目录，部署时改为 drivers/）
```

- 打包/安装/卸载工具：扩展 `sdk/plugin_tool.py` 同款模式，新增 `tools/driver_tool.py`：
  - `driver_tool.py pack <dir>` — 生成 .odp（自动写 CHECKSUMS）
  - `driver_tool.py install <odp> <drivers_dir>` — 校验 → 解压 → 二次校验 → JSON 输出结果（与 plugin install 协议一致）
  - `driver_tool.py uninstall <id> <drivers_dir>` — 卸载
- CMake：`drivers/CMakeLists.txt` 为每个驱动建独立 target（`driver_zlg` / `driver_peak` / `driver_kvaser` …），仅链接 Qt6::Core/Qt6::Gui，输出到 `build/bin/drivers/<id>/`，`build.py deploy` 一并部署。

## 七、加载、生命周期与隔离

### 7.1 DriverRegistry（新增 `src/core/driver/driverregistry.*`）

```cpp
class DriverRegistry : public QObject
{
    Q_OBJECT
public:
    static DriverRegistry *instance();

    struct DriverEntry {
        QString driverId, displayName, version, iconPath;
        bool builtin = false;        // 内置（静态编译）驱动
        bool loaded = false;         // 外置 .dll 已加载
        QString disabledReason;      // 预检失败原因（版本/ABI/架构不符）
        QJsonArray devices;          // driver.json devices[]（内置驱动由代码提供）
    };

    void initialize();                       // 启动扫描 + 加载
    void scanAndLoad();                      // 热安装后重扫（增量）
    QList<DriverEntry> drivers() const;

    std::vector<ICanDevice::DeviceInfo> enumerateDevices() const;   // 聚合全部可用驱动
    ICanDevice *createDevice(const QString &driverId, int subType) const; // 外置优先于内置

signals:
    void driversChanged();                   // 设备树刷新
};
```

### 7.2 加载流程（安全预检链）

```
drivers/<id>/driver.json 存在？
  → sha256 校验（对照 CHECKSUMS）
  → QPluginLoader::metaData() 读 IID / abiVersion / arch / minAppVersion
      ✗ 不匹配 → 登记 disabledReason，跳过（主程序不受影响，R5）
      ✓ → loader->load()
           ✗ 失败 → 登记 errorString，跳过
           ✓ → qobject_cast<CanDriverPlugin*> → 注册条目 → emit driversChanged()
```

### 7.3 厂商 DLL 隔离规则（关键）

- 每个驱动的厂商 SDK DLL 放在自己的 `drivers/<id>/vendor/` 下，**驱动代码内部用绝对路径 `QLibrary::load`**（以 `GetModuleFileName(self)` 取自身目录拼接），不走系统 PATH，避免多驱动同名 DLL 串扰；
- 沿用 `candevice_zlg.cpp` 已验证的实践：PE 头预检 64 位（`isDll64Bit`，不触发 DllMain）、共享 DLL 单例**加载后永不卸载**（避免 USB 设备状态被 DllMain 破坏）；
- 搜索顺序升级为：`drivers/<id>/vendor/` → 应用目录 → 应用目录/driver → 厂商安装目录（ZCANPRO 等）→ PATH。

### 7.4 卸载与禁用语义（建议）

- **禁用**：Registry 标记 disabled，设备树隐藏，重启后不加载（`drivers/disabled.json` 持久化）；
- **卸载**：若驱动已加载（.dll 在进程内）→ 标记待删除，**重启时清理目录**（进程内 unload 原生 DLL 有静态析构/DllMain 风险，ZLG 共享单例已有先例注释）；未加载过 → 直接删目录；
- 安装确认弹窗必须明示「原生驱动将在主进程内运行」。

### 8.2 安全边界（与 Python 插件对比，需在评审时明确告知）

- 市场源定位：`exeDir/../market/`（开发/发布 bin 布局）→ `exeDir/market/` → 官方占位 URL（`https://market.openbus.local/market.json`，发布时替换）。
- `build/bin/drivers/<id>`（CMake 部署的开发 dll 目录，无 driver.json）会被登记为「外置 · 不可用（缺少 driver.json）」条目——诊断信息，属设计内行为；安装正式包后由可用条目覆盖。
- 已知 UI 打磨项：「＋新增设备」树节点点击热区较窄（待后续优化）；市场图片当前为占位 SVG，正式图片随 market.json 版本化分发。

## 十四、第三方硬件适配路线图（市占驱动，2026-08-19 规划，待评审）

> 需求：盘点市面主流第三方 CAN 硬件（闭源/开源），按市场占有率决定驱动插件开发
> 优先级；统一走现有驱动插件框架（§五 CanDriverPlugin + §六 .odp + DriverRegistry +
> §十三统一市场），主程序零改动；目标是支持尽可能多的设备，扩大 openbus 适用范围。
> 本节是对 §九初版矩阵的市占驱动修订与全景扩展（§九 P0 三家已全部落地）。

### 14.1 目标与原则

**目标**：每一款市面主流 CAN 硬件，用户在 openbus「插件市场」中都能找到对应驱动，
一键安装即用。

**三条原则**：

1. **统一框架不变体**：一切接入走 `CanDriverPlugin` 五虚函数契约 + `driver.json` +
   `drivers/<id>/` 目录 + `.odp` 分发（§四/§五/§六）；新厂商接入不改主程序代码，
   仅新增目录与 `add_subdirectory`。
2. **协议聚合优先**：开源协议类（GS_USB / SLCAN）一份驱动可覆盖 N 家硬件
   （含兼容固件与 DIY 生态），投入产出比远高于逐厂商 SDK 封装，优先实施。
3. **闭源 SDK 按市占排期**：以用户设备保有量（而非厂商知名度）排序，同时评估
   SDK 可得性、分发授权、适配成本三因素；授权受限的一律走 `vendorSdk.bundled: false`
   + 安装弹窗引导用户自取（ZLG 模式，§7.3）。

### 14.3 市场占有率定性评估

> 说明：CAN 接口卡市场无权威整体份额统计（各分析机构口径不一，如「PC-based CAN
> 分析仪」类目 2025 年统计约 48.5% 增长占比等，均不能直接代表设备保有量结构），
> 以下为社区口碑（Reddit/EEVblog）、国内电商在售结构、开源生态工具支持面综合的
> **定性分层**，用于排期而非精确数字。

| 市场 | 第一梯队 | 第二梯队 | 长尾 |
|------|----------|----------|------|
| 国内桌面工具 | ZLG 系生态（正品 + 创芯/广成兼容克隆 + 淘宝 ZLG 风格仿款），估计合计过半 | PEAK/Kvaser（外企/正规工业采购）；同星（汽车工具链） | 淘宝 SLCAN 杂牌、DIY |
| 国际 | PEAK、Kvaser（平价双雄） | Vector（OEM/产线高端垄断）、ixxat | NI/Softing/ETAS（专用场景） |
| 开源社区 | GS_USB + SLCAN（SavvyCAN/Busmaster/cangaroo 等标配支持） | candleLight 系周边 | panda 等 |

**结论**：对 openbus（国产桌面 CAN 分析工具定位）而言——

1. 国内用户硬件主力是 **ZLG 系生态**（已接 zlg，创芯/广成待接）；
2. 数量上最大的单一群体是 **SLCAN 长尾**（一份驱动全覆盖）；
3. 开源社区与极客群体入口是 **GS_USB**（一份驱动全覆盖）；
4. Vector/NI 等高端用户被厂商自有工具（CANoe/INCA/LabVIEW）锁定的比例高，
   第三方工具对其吸引力有限，适配优先级低于市占直觉。

### 14.5 统一适配方法论（三类载体 SOP）

所有驱动最终交付物一致：`drivers/<id>/`（plugin.h/.cpp + driver.json +
CMakeLists.txt + market/assets）→ `add_subdirectory` → `scripts/driver_tool.py pack`
→ `.odp` → `make_market.py` 上架。差异在「设备后端实现层」的三类载体：

#### 14.5.1 闭源 SDK 类（zlg/peak/kvaser 模式复刻）

七步 SOP（以创芯/广成/Vector/ixxat 为候选）：

1. **SDK 获取与授权评估**：官网/注册下载；确认 dll 能否随 `.odp` 分发，不能则
   `vendorSdk: { dll, bundled: false, license }` + 安装弹窗引导自取（zlg 先例）；
   PCAN 类需保留版权声明（随包 LICENSE）。
2. **后端封装** `src/core/candevice_<id>.h/.cpp`：`QLibrary` 以驱动自身目录为基准
   绝对路径加载（§7.3 隔离），DLL 缺失时优雅降级（enumerate 返回空 + 可用性诊断）；
   厂商特有能力（硬件滤波/错误帧/总线负载/ISO 切换）走 `VendorCtrl` 透传不阉割。
3. **插件包装** `drivers/<id>/<id>_driver_plugin.h/.cpp`：QObject + CanDriverPlugin
   五虚函数 + `Q_PLUGIN_METADATA`（IID `com.sin.openbus.CanDriverPlugin/1.0`），
   enumerateDevices/createDevice 委托后端（§5.2 模板）。
4. **清单与构建**：driver.json（devices[] 设备表 + vendorSdk）、CMakeLists.txt
   （复用后端源码编入 target、输出 `build/bin/drivers/<id>/`）、根 CMake
   `add_subdirectory(<id>)`。
5. **打包上架**：`driver_tool.py pack` 出 `.odp`（含 CHECKSUMS.sha256）→
   `make_market.py` 聚合 market.json（icon/summary/readme/devices 简表内联）。
6. **GUI 实测清单**（每驱动必测）：市场安装热加载 → 设备树分区出现 → 枚举 →
   收发 → CAN FD（如支持）→ 时间戳归一化 → 禁用/卸载 → 卸载后重启清理干净
   （§7.4）；无硬件时至少验证「DLL 缺失优雅降级 + 安装/卸载链路」。
7. **授权合规**：vendor/LICENSE 随包或安装弹窗明示商用条款（§十一既有要求）。

#### 14.5.2 开源协议聚合类（candle / slcan，单驱动多设备）

与 SDK 类的差异点：

- **依赖引入**：`candle` 需 libusb-1.0（Windows 走 WinUSB WCID 免驱；建议 vendored
  源码或预编译 MinGW x64 包进 third_party/，随驱动 target 链接，不进主程序）；
  `slcan` 用 Qt6::SerialPort，零新增依赖。
- **枚举策略**：candle 按 VID/PID 白名单扫描 + GS_USB 协议 probe（设备名回读）；
  slcan 扫描系统串口（名称正则过滤）+ 握手探测（`V\r\n` 版本号应答确认在线）。
- **driver.json devices[] 建模**：按「硬件型号/固件方言」列条目（如 candle：
  CANable 1.0 / CANable 2.0 / cantact / candleLight / 其他 gs_usb 兼容；
  slcan：Lawicel CANUSB 风格 / ESP32 slcan / USBtin），设备表即兼容清单，
  市场详情页直接展示（§13.7 阶段 B devices 简表）。
- **时间戳**：GS_USB 有 USB 帧到达时间戳（标记 hardware）；SLCAN 无 →
  `hasHwTimestamp: false`，Trace 时间轴标注「软件接收时间」（§1.3 风险 2 /
  §十一既有约定，落实为 driver.json 字段，见 §14.6）。
- **方言风险**：SLCAN 各厂 AT 命令集碎片化 → 只实现保守公共子集
  （O/C/V/N/F/M）+ 能力探测降级，不承诺厂商私有扩展。
- **无真机开发**：slcan 可用 com0com 虚拟串口对 + 脚本模拟设备应答全流程开发；
  candle 建议采购 CANable 2.0（$25–40）实测，协议层可用 usb 抓包样本回放开发。

#### 14.5.3 OEM/兼容类（创芯、广成、研华）

先验证兼容假设，再二选一落地：

- **预研验证**：① 创芯——官方宣称函数库兼容 ZLG（ControlCAN 风格）：样机 +
  zlgcan.dll 替换为其 dll 后试枚举/收发；② 研华 USB-4680——PCAN OEM 假设：
  装研华驱动后直接用现有 peak 驱动枚举实测。
- **方案 A（并入现有驱动）**：API 二进制级兼容（同导出函数签名）时，仅在
  zlg/peak 的 driver.json `devices[]` 增补型号 + 驱动内 VID/设备类型白名单扩展。
  优点零新代码；风险：设备型号表与授权文案混杂。
- **方案 B（独立驱动）**：函数名兼容但 dll 名不同/设备类型号空间冲突时，
  拷贝后端实现改 dll 名与授权文案，独立 `drivers/<id>/`。优点隔离清晰、
  可独立卸载；缺点代码重复（可抽公共模板）。
- **决策规则**：二进制兼容 → A；否则 → B。默认 B（隔离优先），A 仅用于
  验证确凿且型号极少的场景（如研华试点）。

### 14.6 框架扩展点（✅ 已随 v2.2 第一批落地，2026-08-18；均为向后兼容增量）

1. `driver.json` 新增可选字段（✅ registry 解析 + `driver_tool.py` 校验已支持）：
   - `devices[].hasHwTimestamp`（bool，缺省 true）——时间戳来源标识，
     DeviceConnectionTab/Trace 列头展示（slcan 全 false）；
   - `devices[].vid` / `pid`（string，hex）——协议类驱动枚举展示辅助；
   - `vendorSdk.dll` 支持字符串数组（多 dll 依赖，如创芯可能同时依赖两个库）。
2. market.json 设备简表增「时间戳」能力列（✅ `make_market.py` 已透传 hasHwTimestamp/vid/pid）。
3. `third_party/libusb`（candle 依赖）引入评估（✅ 已决策：**不做 vendored 链接**，
   改为运行时 `QLibrary` 动态加载 `libusb-1.0.dll`——搜索序 `drivers/candle/vendor` →
   应用目录 → PATH，共享单例永不卸载；DLL 由 `scripts/download_libusb.py` 从 PyPI
   官方 wheel 提取（PE 头校验 x64），经仓库 `driver/` 目录随 POST_BUILD 整目录拷贝分发，
   `vendorSdk.bundled=false` 声明市场包不含该 LGPL 运行库）。

### 14.8 风险与对策（增量，并入 §十一）

| 风险 | 影响 | 对策 |
|------|------|------|
| SLCAN 方言碎片化（各厂命令集不一致） | 部分杂牌设备无法打开/乱码 | 保守公共子集 + `V` 探测能力降级；兼容清单明示「已验证型号」，未验证型号标注实验性 |
| 无真机开发 candle 驱动 | 协议细节踩坑（bittiming/时间戳） | 采购 CANable 2.0（$25–40）；协议以 candle-usb 官方固件源码为准 |
| libusb 引入的构建/分发复杂度 | Windows 免驱依赖 WinUSB WCID 支持 | vendored + 仅驱动 target 链接；老系统不支持 WCID 时文档指引手动装 WinUSB |
| 创芯/广成 API 兼容性宣称与实际不符 | 预研结论推翻排期 | 先购样机验证再排实施（§14.5.3 预研前置） |
| Vector/ixxat 用户被 CANoe 等自有工具锁定 | 适配投入产出比低 | 维持 P2 需求驱动，不主动投入 |
| 长尾硬件枚举误报（VID/PID 撞号） | candle 驱动枚举到非 CAN 设备 | 白名单严格制 + probe 应答校验，宁可漏不可错 |

## 1. 现状审计（代码事实）

### 1.1 已落地且仍可用的部分

```
MainWindow
  └─ PluginManager::initialize()          # mainwindow_setup.cpp 已调用
       ├─ discoverPlugins()               # 扫描 <base>/plugins/*/plugin.json
       ├─ onFrameReceived()               # 帧热路径已接（frameflow）
       ├─ handleHostMessage()             # 控制方法表齐全（frames/dbc/signals/workspace/...）
       └─ PluginHost (QProcess)           # 设计为拉起 Python 宿主
            └─ JSON-RPC over stdin/stdout # newline-delimited

sdk/sin/                                  # 插件侧 API（_transport → stdout）
plugins/*/main.py + plugin.json           # 大量 PyQt6 业务插件
```

要点：

- **单宿主多插件**：历史上是一个 `sin_host.py` 进程内加载多个插件模块（非每插件一进程）。
- **控制 + 数据混在同一管道**：激活/命令/DBC 查询与 `frameReceived` 批量帧都走 stdin/stdout JSON。
- **订阅制已在 C++ 侧落地**：`subscribeFrames` → `m_frameSubscribers` 门控；无订阅 = 零帧推送开销。
- **市场/安装链**：`installPackage` / `uninstallPlugin` / Market 面板与 PluginManager 的连接仍在。

### 1.2 已断链的部分（必须修复）

| 组件 | 期望路径 | 现状 |
|------|----------|------|
| Python 宿主 | `scripts/sin_host.py` | **文件不存在**（CMake 亦打印 `Plugin host scripts not found`） |
| 打包辅助 | `plugin_tool.py` / `driver_tool.py` | 一并删除 |
| 运行时 | `PluginManager::startHostIfNeeded()` | `QFileInfo::exists(m_hostScriptPath)` 失败 → warn 并 return |
| 结果 | 插件无法 activate、收不到帧、REST/ZMQ 均未建立 | 市场可发现，**进程间桥失效** |

历史说明：2026-08-23 文档记录的「链路审计 9 项修复 + E2E」针对的是当时仍存在的 `sin_host.py` + stdin/stdout 方案；当前树已回退到「有协议、无宿主」状态。

### 1.3 与设计文档的偏差

| 文档宣称（`插件系统方案.md` §一） | 代码实际 |
|----------------------------------|----------|
| Named Pipe 双通道 + 二进制帧 | 实际为 stdin/stdout JSON（且宿主脚本缺失） |
| 每插件一进程 | 实际为单 Python 宿主多插件 |
| ZMQ / REST | 均未实现 |

本方案不再延续 Named Pipe / 纯 stdin 作为目标传输，改为 **ZMQ（数据）+ REST（控制）**。

## 2. 目标架构

### 2.1 原则

1. **主从隔离**：主进程 `openbus.exe`（C++ Qt6）；插件侧 Python + PyQt6，独立进程，崩溃不拖垮主程序。
2. **双通道分离**：
   - **数据通道（ZMQ）**：高频、单向为主（主→插件帧/信号批量）；可扩展插件→主的低频二进制回写（如批量统计）。
   - **控制通道（REST）**：低频、请求/响应（激活、命令、DBC、workspace、选中帧查询等）。
3. **同一工具链**：主程序与插件解释器均基于 **MSYS2 UCRT64**（与现有 `scripts/build.py` 一致），避免混用 MSVC Python / 原生 Qt 导致 ABI/DLL 混乱。
4. **SDK 稳定**：插件作者继续 `import sin`；传输层替换对业务插件透明。
5. **无订阅 = 零推送**：保留现有订阅门控语义。

### 2.2 进程与通道总览

```
┌──────────────────────────── openbus.exe (C++ / Qt6) ────────────────────────────┐
│  Trace / Graphic / Device                                                       │
│         │                                                                       │
│         ▼                                                                       │
│  PluginManager                                                                  │
│    ├─ PluginRestServer   (控制)  HTTP 127.0.0.1:<ctrl_port>                     │
│    ├─ PluginZmqHub       (数据)  ZMQ PUB  tcp://127.0.0.1:<data_port>            │
│    └─ PluginProcessMgr   QProcess → MSYS2 python + sin_host.py                  │
└────────────┬───────────────────────────────┬────────────────────────────────────┘
             │ REST (JSON)                   │ ZMQ PUB (binary / multipart)
             ▼                               ▼
┌──────────────────────────── sin_host.py (Python / PyQt6) ───────────────────────┐
│  REST Client (控制)          ZMQ SUB (数据)                                     │
│         │                         │                                             │
│         ▼                         ▼                                             │
│  sdk/sin/*  (外观不变)  ←── _transport (REST) + _databus (ZMQ)                   │
│         │                                                                       │
│  plugins/A  plugins/B  ...（同进程多插件，Phase 1；Phase 2 可拆每插件一进程）      │
└─────────────────────────────────────────────────────────────────────────────────┘
```

**Phase 1 默认**：恢复「单宿主多插件」以最快打通；ZMQ topic 按插件名过滤。  
**Phase 2（可选）**：每插件一进程 + 独立 SUB，贴近旧 v2 隔离目标。

### 2.3 为何 ZMQ + REST（相对 stdin/stdout）

| 维度 | stdin/stdout JSON（旧） | ZMQ + REST（本方案） |
|------|-------------------------|----------------------|
| 帧吞吐 | JSON+hex，易堵控制面 | PUB/SUB 二进制，控制面不被淹没 |
| 调试 | 与日志混流，MergedChannels 易污染 | HTTP 可用 curl；ZMQ 可用独立探针 |
| 扩展 | 难接第二消费者 | 多 SUB（分析器/录制旁路）零改主协议 |
| MSYS2 | 可用但脆弱 | ucrt64 有 `mingw-w64-ucrt-x86_64-zeromq` 等包 |
| 安全 | 本机管道 | 默认仅绑定 `127.0.0.1` + 启动令牌 |

## 3. 运行环境（MSYS2）

### 3.1 依赖（UCRT64）

| 角色 | 包 / 组件 |
|------|-----------|
| 主程序构建 | 现有 Qt6 / cmake / ninja（已有） |
| C++ ZMQ | `mingw-w64-ucrt-x86_64-zeromq` + cppzmq 头文件（或 vendoring `third_party/cppzmq`） |
| C++ HTTP | 优先 **Qt HTTP Server**（若 Qt 版本具备）或轻量 **cpp-httplib** 单头 vendoring |
| Python | MSYS2 `mingw-w64-ucrt-x86_64-python` + `python-pyzmq` + PyQt6（与主程序同前缀） |
| 查找顺序 | `SIN_PYTHON` > `<exe>/runtime/python` > PATH 上的 ucrt64 `python.exe` |

启动宿主时 `QProcess` 环境应包含：

- `SIN_SDK_DIR` / `SIN_PLUGINS_DIR`（已有）
- `SIN_CTRL_URL`（例：`http://127.0.0.1:17320`）
- `SIN_ZMQ_ENDPOINT`（例：`tcp://127.0.0.1:17321`）
- `SIN_SESSION_TOKEN`（主进程生成的随机令牌，REST 鉴权）
- `PATH` 前置 ucrt64 `bin`，保证插件加载到同一套 DLL

### 3.2 端口与生命周期

1. 主进程 `initialize()`：先起 REST + ZMQ，再 `QProcess` 拉起 `sin_host.py`。
2. 宿主 `hello`：REST `POST /v1/session/hello`，上报 PID、协议版本、能力集。
3. 主进程关机：`POST /v1/session/shutdown` → 等待退出 → 再关 ZMQ/REST；保留现有 `kStopped` 防僵尸逻辑。

## 4. 控制通道（REST）

### 4.1 约定

- Base：`http://127.0.0.1:<ctrl_port>/v1`
- 鉴权：Header `X-Sin-Token: <SIN_SESSION_TOKEN>`
- Body：JSON；错误形如 `{ "error": { "code": -32601, "message": "..." } }`（兼容旧 JSON-RPC 错误码语义，便于 SDK 迁移）
- 超时：SDK 默认 5s（与现 `_transport.send_request` 一致）

### 4.2 资源映射（兼容现有方法名）

旧 JSON-RPC `method` 映射为 REST，便于渐进替换：

| 方向 | 旧 method | REST |
|------|-----------|------|
| 主→宿 | `activate` / `deactivate` | `POST /plugins/{name}/activate` · `POST .../deactivate` |
| 主→宿 | `executeCommand` | `POST /commands/{id}/execute` |
| 主→宿 | `fileOpened` | `POST /events/file-opened` |
| 主→宿 | `shutdown` | `POST /session/shutdown` |
| 宿→主 | `subscribeFrames` | `POST /subscriptions/frames` `{ "plugin": "..." }` |
| 宿→主 | `frames.getSelected` | `GET /frames/selected` |
| 宿→主 | `frames.getRecent` | `GET /frames/recent?count=100` |
| 宿→主 | `sendFrame` | `POST /frames/send` |
| 宿→主 | `output.append` / `output.clear` | `POST /output/append` · `POST /output/clear` |
| 宿→主 | `registerCommand` | `POST /commands/register` |
| 宿→主 | `signals.decode` / `encode` | `POST /signals/decode` · `POST /signals/encode` |
| 宿→主 | `dbc.*` / `files.*` / `workspace.*` | 同名资源路径 `/dbc/...` `/files/...` `/workspace/...` |
| 宿→主 | `pluginWindowClosed` | `POST /plugins/{name}/window-closed` |
| 宿→主 | `log` | `POST /log` |

> 实现策略：C++ 侧保留现有 `handleXxx` 实现，仅把「从 stdin 解析 method」换成「HTTP 路由分发」；Python SDK 把 `send_request/send_notification` 换成 HTTP client。

### 4.3 谁做 Server？

- **主进程为 REST Server**（权威数据在主进程：Trace 选中帧、DBC、工程路径）。
- 插件宿主为 REST Client（查询/发命令）。
- 主→插件的「推送型控制」（activate 等）有两种等价实现，推荐 **A**：
  - **A（推荐）**：主进程对宿主再开一个 **回调 HTTP**（宿主 listen 随机端口，hello 时回传），或复用 ZMQ 上的 `CTRL` topic。
  - **B**：宿主长轮询 `GET /events`——实现简单但延迟差，不推荐。

Phase 1 建议：activate/deactivate/executeCommand 走 **ZMQ multipart 控制帧**（低频），其余查询类走 REST 主 Server——避免再嵌一套 HTTP Server 在 Python 里。若希望「控制纯 REST」，则采用回调端口方案 A。

**本文拍板（Phase 1）**：

- 插件→主：**纯 REST**（主进程 Server）
- 主→插件控制通知：`ZMQ` topic `ctrl`（与数据 topic 分离）
- 主→插件数据：`ZMQ` topic `frames` / `signals`

这样 REST 只需单向（插件调主），实现量最小且满足「控制指令走 REST」的产品表述（指令发起方是插件 SDK；主→插件生命周期通知属数据面旁路）。

## 5. 数据通道（ZMQ）

### 5.1 Socket 角色

| 端 | Socket | Endpoint |
|----|--------|----------|
| 主进程 | PUB | `tcp://127.0.0.1:<data_port>` |
| 宿主 | SUB | 连接上述 endpoint；subscribe `frames` / `signals` / `ctrl` |

可选后续：插件→主 `PUSH/PULL` 用于高频回写（当前 `sendFrame` 走 REST 即可）。

### 5.2 帧消息格式（建议 v1 二进制，避免 JSON+hex）

Multipart：

1. topic：`frames`（UTF-8）
2. header：固定 16 字节  
   - magic `OBUS` (4)  
   - version `uint16`  
   - msg_type `uint16`（1=FRAME_BATCH）  
   - frame_count `uint32`  
   - reserved `uint32`
3. body：紧凑帧数组（与历史方案一致）

单帧布局（16 + N）：

```
can_id u32 | flags u8 | dlc u8 | channel u8 | data_len u8 | ts_ns u64 | data[N]
```

flags：bit7 ext, bit6 fd, bit5 brs, bit4 esi, bit3 dir(Tx=1)

批量上限：沿用现逻辑，每包 ≤100 帧；主进程 100ms timer flush。

### 5.3 订阅语义

1. 插件 `context.on_frame(cb)` → SDK `POST /subscriptions/frames`。
2. `PluginManager` 记入 `m_frameSubscribers`。
3. 仅当集合非空时缓冲并 PUB；topic 可带插件过滤：`frames.<plugin>` 或统一 `frames` 由宿主内分发（Phase 1 用后者，与旧单宿主一致）。

### 5.4 ctrl topic（主→插件通知）

JSON 文本帧即可（低频）：

```json
{ "jsonrpc": "2.0", "method": "activate", "params": { "plugin": "...", "directory": "...", "main": "main.py" } }
```

宿主 SUB 线程投递到 Qt 主线程 / 宿主事件队列（保持与旧 stdin 读线程模型类似）。

## 8. 风险与对策

| 风险 | 对策 |
|------|------|
| ZMQ/HTTP 依赖增大安装面 | MSYS2 包 + 可选 vendoring；便携包脚本显式拷贝 DLL |
| 端口冲突 | 绑定 `127.0.0.1:0` 取临时端口，经环境变量交给宿主 |
| SUB 慢导致丢帧 | 主端 HWM + 已有 50k 缓冲丢最旧；宿主侧队列有界 |
| Token 泄漏 | 仅环境变量、不写日志明文；仅本机回环 |
| 与旧插件二进制协议假设 | SDK 遮罩；第三方若直接 parse stdin 需改用 SDK |

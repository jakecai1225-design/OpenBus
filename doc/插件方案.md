> 运行环境：双方 **MSYS2 UCRT64**

## 1. 为何不用 REST / 不用继续 stdin

- 控制面本质是本机 **RPC**，已有完整 `method` 表；REST 增加 HTTP 栈且主→插件仍需旁路。
- stdin/stdout 曾可用，但控制与高频帧混流，MergedChannels 易污染；恢复后也应升级。
- 纯 ZMQ：一个依赖族（libzmq + pyzmq），双套接字职责清晰。

## 2. 架构

```
openbus.exe                          sin_host.py
┌─────────────────────┐              ┌─────────────────────┐
│ PluginManager       │              │ plugin modules      │
│        │            │              │        ▲            │
│        ▼            │              │        │            │
│ PluginHost (QProcess│              │ sdk/sin/*           │
│  + PluginZmqHub)    │              │  _transport (DEALER)│
│  ROUTER  ◄──JSON──► │◄────────────►│  ctrl JSON-RPC      │
│  PUB     ──binary─► │─────────────►│  _databus (SUB)     │
└─────────────────────┘              └─────────────────────┘
         tcp://127.0.0.1:<ephemeral>
```

环境变量（主进程启动宿主时注入）：

| 变量 | 含义 |
|------|------|
| `SIN_ZMQ_CTRL` | 例 `tcp://127.0.0.1:52301`（ROUTER endpoint） |
| `SIN_ZMQ_DATA` | 例 `tcp://127.0.0.1:52302`（PUB endpoint） |
| `SIN_SDK_DIR` / `SIN_PLUGINS_DIR` | 既有 |

端口：绑定 `tcp://127.0.0.1:*`，用 `ZMQ_LAST_ENDPOINT` 取实际地址。

## 3. 控制通道（JSON-RPC over ZMQ）

- 消息体：与历史 stdin 方案相同的 JSON 对象（可无尾部 `\n`）。
- DEALER identity 固定为 `sin-host`，便于 ROUTER 定向发送。
- 宿主启动后发 `host.hello` 通知；主进程可据此确认在线。
- 方法表：沿用 `PluginManager::handleHostMessage` / 文档契约（activate、subscribeFrames、frames.*、dbc.*、signals.*、workspace.*、sendFrame、output.* 等）。
- **帧推送不再走** `frameReceived` JSON；改走数据通道。宿主仍可识别 `frameReceived` 作兼容兜底（可选）。

---

## 4. 数据通道（二进制 PUB）

Multipart：

1. topic：`frames`（UTF-8）
2. payload：

```
offset  size  field
0       4     magic "OBUS"
4       2     version = 1 (u16 LE)
6       2     msg_type = 1 FRAME_BATCH (u16 LE)
8       4     frame_count (u32 LE)
12      …     frames
```

单帧：

```
can_id u32 LE | flags u8 | dlc u8 | channel u8 | data_len u8
timestamp_ns u64 LE | data[data_len]
```

flags：bit7 ext, bit6 fd, bit5 brs, bit4 esi, bit3 Tx

订阅：插件 `context.on_frame()` → `subscribeFrames`（控制面）→ 主进程才 PUB；无订阅 = 不编码不发送。

批量：≤100 帧 / 包；主进程 ~100ms flush（与现逻辑一致）。

## 5. 进程模型（Phase 1）

- **单 Python 宿主、多插件**（恢复历史行为）。
- `PluginHost`：QProcess 生命周期 + 崩溃退避重启；消息走 ZMQ，不再依赖 stdin 业务协议。
- stderr 可单独记录宿主日志。

## 6. 依赖（UCRT64）

| 组件 | 包 |
|------|-----|
| C++ | `mingw-w64-ucrt-x86_64-zeromq` + `cppzmq`（`zmq.hpp`） |
| Python | `mingw-w64-ucrt-x86_64-python` + `mingw-w64-ucrt-x86_64-python-pyqt6` + `mingw-w64-ucrt-x86_64-python-pyzmq` |

插件宿主 **强制** 使用 MSYS2 前缀内的 Python（默认 `C:/msys64/ucrt64/bin/python.exe`）：

1. `SIN_PYTHON`（须能 `import PyQt6` + `import zmq`）
2. `MSYSTEM_PREFIX` / `MINGW_PREFIX` 下的 `bin/python.exe`
3. 常见根目录 `C:/msys64`、`D:/msys64`（及 `SIN_MSYS2`）→ **ucrt64 → clang64 → mingw64**
4. 可选便携 `runtime/python`（同样须带 PyQt6/pyzmq）
5. PATH 上的 `python` **仅当** 解析路径落在 `*/ucrt64|clang64|mingw64/bin/` 且通过 PyQt6/zmq 探测

拒绝 Windows Store / python.org 等非 MSYS2 解释器。宿主进程环境会注入对应前缀的 `PATH`、`MSYSTEM`、`MINGW_PREFIX` 与 Qt6 `QT_PLUGIN_PATH`。

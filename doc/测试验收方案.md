# openbus 全功能测试验收方案

> **版本**: v2.0
> **日期**: 2026-08-20
> **范围**: 各板块功能点开发完毕后的整体业务级验收测试（v2.2 基线）
> **执行者**: AI 助手（自动化测试开发与执行：Qt Test 集成测试 + offscreen UI 驱动 + 人工抽查清单）
> **状态**: 待评审（v2.0 修订：弃截图走查，改自动化分层验证）

---

## 一、测试目标与范围

### 1.1 目标

以**业务流程为主线**（非模块孤测），对 openbus 各板块做一次端到端验收：

1. 验证「采集 → 解析 → 分析 → 记录 → 回放 → 导出」完整业务闭环可用
2. 验证各功能入口（菜单 / ActivityBar / 侧边栏 / 快捷键 / 终端命令）行为正确
3. 暴露跨模块集成问题（信号联动、状态同步、资源清理）
4. 形成可追溯的测试报告与缺陷清单，作为 v2.2 验收依据

### 1.2 范围内（8 大业务域 + 4 专项）

| # | 业务域 | 覆盖内容 |
|---|--------|---------|
| 1 | 文件与离线分析 | 打开/导入 BLF·ASC·CSV、Trace 显示、导出 ASC·CSV |
| 2 | 回放 | 加载文件回放、变速、进度拖拽、播放/暂停/停止 |
| 3 | 采集与录制 | 模拟器（无硬件）/ 真实设备（有硬件）、录制启停、环形缓冲 |
| 4 | 发送 | 信号发送、周期发送、Tx 帧回显 |
| 5 | DBC 与信号 | DBC 加载、信号树、解码、双击追踪到 Graphic、Data Window |
| 6 | Graphic 波形 | 多信号、缩放平移、卡尺测量、游标 |
| 7 | 设备与市场 | 设备连接面板、插件市场（搜索/详情/安装/启停/卸载）、离线 .odp/.opk 安装 |
| 8 | 插件与工程 | 5 个 Python 插件功能、工程新建/保存/恢复、命令行终端 |
| S1 | UI 专项 | 主题切换、面板停靠、标签页拆分、图标渲染、无遮挡错位 |
| S2 | 性能专项 | 大 BLF 加载耗时、1M 帧环形缓冲、视窗刷新流畅度 |
| S3 | 稳定性专项 | 长时间录制、重复打开关闭、异常文件容错 |
| S4 | 数据正确性专项 | 导出-重导入闭环比对、信号解码抽查比对 DBC 定义 |

### 1.3 范围外

- 单元测试 / 白盒测试（开发阶段已覆盖）
- 多操作系统（仅 Windows 本机）
- 极限性能压测（如 100 万帧全量渲染帧率）——仅做基本性能验证
- S01-S12 待实施需求（需求文档 v2.0 中未完成项）不在验收范围

## 二、测试策略

### 2.1 验证方式（v2.0：自动化分层验证，替代截图走查）

> v1.0 采用 AI 截图 GUI 走查，实测效率过低（每用例分钟级、易受桌面环境干扰）。v2.0 改为**测试代码自动化为主 + 少量人工抽查**的三层金字塔：

| 层 | 方式 | 原理 | 覆盖 | 单例耗时 |
|----|------|------|------|---------|
| **L1 核心逻辑集成测试** | 新建 `tests/` Qt Test 工程，直接调用 core/models 层 API（BlfReader / FilterEngine / DbcManager / CanSimulator / Recorder / Player / CanTraceModel / MarketIndex / DriverRegistry / ProjectManager...），断言数据结果 | 数据层直测，不经 UI；已确认全部核心类位于 `src/core`+`src/models`，无 UI 依赖 | 文件 I/O、过滤语义、DBC 解码、录制/回放/导出闭环、市场索引、驱动注册、性能计时 | 毫秒级 |
| **L2 UI 驱动测试** | `QT_QPA_PLATFORM=offscreen` 无头启动关键 UI，QTest 模拟事件 + 控件树断言（如过滤后 `CanTraceProxyModel::rowCount()` 变化、面板切换后当前 widget） | 无窗口渲染，控件级验证；不依赖桌面环境 | 标签页生命周期、面板联动、模型-视图联动、命令行终端 | 秒级 |
| **L3 人工抽查** | 一次性 GUI 走查清单（仅视觉项，约 15 项），用户或 AI 单轮走查 | 人眼判断美观/遮挡/图标效果 | 主题、图标渲染、布局美观、悬停提示 | 分钟级×~15 项 |

**优势**：
1. 测试代码一次编写、永久回归——后续版本验收直接重跑，秒级出结果
2. 断言即证据：失败自动打印数据 diff（帧数/ID/物理值），比截图客观
3. L2 不受桌面遮挡/分辨率/输入法干扰（v1.0 实测问题）
4. spdlog 日志检查（`logs/`）作为全程辅助：每个测试套件跑完扫一次 error 级日志

**验证方式归属**：原 v1.0 的「日志验证/产物验证/数据比对」并入 L1 断言（测试直接读产物文件比对数据）；「GUI 走查」仅保留 L3 视觉清单。

### 2.2 硬件分级（关键决策点 D1）

| 级别 | 环境 | 适用 |
|------|------|------|
| **L0 无硬件** | 内置模拟器（`sim` 开关）+ 文件回放 | 本次验收**主体**，全部用例默认 L0 |
| **L1 真实硬件** | ZLG / PCAN / Kvaser / candle(GS_USB) / slcan 任一在手 | 设备枚举、真实收发、硬件时间戳用例 |

> **待评审确认**：本次验收手头有哪些真实 CAN 硬件？无硬件的用例标记「L1-待真机」跳过，不阻塞验收。

### 2.3 缺陷分级

| 级别 | 定义 | 处理 |
|------|------|------|
| P0 阻断 | 崩溃、数据丢失、核心流程无法走通 | 立即修复后重测 |
| P1 严重 | 主功能错误但可绕过、内存泄漏 | 阻塞验收，须修复 |
| P2 一般 | 次要功能错误、交互不一致 | 记录，验收后修复 |
| P3 轻微 | 文案/样式/提示问题 | 记录，择机修复 |

## 四、测试计划（v2.0：测试套件开发 + 执行）

> 顺序原则：先搭框架 → L1 数据正确性 → L2 UI 联动 → L3 视觉抽查。
> 每阶段以 ctest 通过率 + 失败数据 diff 为准出，P0/P1 缺陷修复回归后才进入下一阶段。

| 阶段 | 内容 | 产出 | 依赖 |
|------|------|------|------|
| A 测试框架搭建 | 新建 `tests/` CMake 工程：Qt Test 模块、链接 `openbus_core`/`openbus_data`、ctest 接入 `build.py`（新增 test 子命令）、样例测试跑通 | 可执行的 tests 骨架 | 无 |
| B1 文件 I/O 套件 | `test_canfileio`：BLF/ASC 读（帧数/首末帧比对）、导出 ASC/CSV、导出-重导入闭环、截断/乱码文件容错 | 对应 TC/ST 数据层用例 | A |
| B2 过滤引擎套件 | `test_filterengine`：表达式语义全表（运算符/语法糖/非法式）、按列筛选 | 对应 TF 数据层用例 | A |
| B3 Trace 模型套件 | `test_tracecore`：CanTraceModel/Proxy/Viewport——覆盖模式、环形缓冲上限、帧计数、排序比较器 | 对应 TF/RC/ST 数据层用例 | A |
| B4 DBC 套件 | `test_dbc`：加载解析、信号解码正确性抽查（raw×factor+offset 手算比对）、多库并存/卸载、异常 DBC 容错 | 对应 DB 数据层用例 | A |
| B5 采集录制回放套件 | `test_sim_rec_play`：CanSimulator 产帧 → Recorder 落盘 → 重载帧比对 → Player 时间轴推进/变速；发送链路（CanDeviceManager + 模拟回环） | 对应 RC/PB/SD 数据层用例 | A |
| B6 市场与驱动套件 | `test_market_driver`：MarketIndex 解析本地 market.json（3 驱动条目）、.odp sha256 篡改拒绝、DriverRegistry 扫描/禁用/延迟卸载状态机 | 对应 MK 数据层用例 | A |
| B7 工程与配置套件 | `test_project`：工程保存/恢复字段、书签、过滤预设、会话状态 | 对应 PR 数据层用例 | A |
| C L2 UI 驱动套件 | `test_ui_offscreen`：offscreen 启动 MainWindow → 8 面板切换断言 → Trace/Graphic 标签页创建/关闭生命周期 → 过滤输入联动 rowCount → 终端命令 sim on/off 生效 | 对应 SM/UI/CM 行为类用例 | B1-B7 |
| D L3 人工抽查 + 专项收尾 | 视觉清单一轮走查（~15 项：主题/图标/悬停/布局）；大文件加载计时与内存基线（L1 计时断言）；30 分钟挂机稳定性；全量日志扫描 | 验收报告 | C |

**里程碑**：
- M1（A+B1-B4 完成）：离线分析与数据正确性验收（核心资产）
- M2（B5-B7 完成）：采集/回放/市场/工程链路验收
- M3（C 完成）：UI 联动验收
- M4（D 完成）：视觉抽查与专项收尾，输出最终测试报告

**准入**：本方案 v2.0 评审通过。
**准出**：见 §六 通过标准。
**回归**：后续版本验收直接 `build.py test` 重跑全部套件，秒级出结果。

## 七、风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| 无真实 CAN 硬件 | 设备/发送/UDS 真机链路无法验证 | 以模拟器+文件覆盖 L0；L1 用例标记「待真机」列入遗留清单，不阻塞准出 |
| 测试代码与实现共享头文件（测试非黑盒） | 单测可能掩盖 UI 参数化错误 | 断言以「需求语义」为准（如帧数/物理值），不复制实现常量 |
| 单例状态串扰（DbcManager 等进程级单例） | 套件间相互影响 | 每套件独立进程（ctest 每套件一进程）+ 套件内 setUp 清理 |
| Python 插件依赖缺失（PyQt6 等） | 插件域全挂 | 测试前检查清单先行验证；缺依赖先补环境再测 |
| 性能数值受本机状态影响 | 基线波动 | 记录测试时机器状态；结论以「是否卡死/明显卡顿」定性为主，数值仅作基线 |
| 用例量大导致执行周期长 | 验收拖期 | 分四个里程碑交付；每里程碑出阶段性报告；B/C 级用例可按用户指示裁剪 |

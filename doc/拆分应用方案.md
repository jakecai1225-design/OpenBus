# 拆分应用方案 — 可行性评估（评审稿）

> **状态：已评审** — 2026-08-19 决议：采用 **方案 D（A + B）**，不做多进程拆分（C1/C2）。
> 细化实施步骤见《[拆分应用实施方案.md](拆分应用实施方案.md)》。
> **日期**：2026-08-19
> **评估对象**：将 openbus 单体应用按业务拆分为多个相对独立的应用程序（分别编码 / 编译 / 调试，最终整合为一个大型应用）的可行性、优劣，以及替代方案对比。

---

## 1. 背景与动机

随着功能持续叠加，当前单体应用在工程效率上暴露出四个痛点：

| 痛点 | 具体表现 |
| --- | --- |
| 编译链接慢 | 改一行代码，等待构建 15~25 分钟才能运行验证 |
| AI 编码效率低 | 单文件 / 单类过大（mainwindow.cpp 3067 行），上下文窗口装不下完整模块；每次改动的反馈回路太长 |
| 调试不便 | 巨型类承担过多职责，断点路径深；任何修改都触发全量链接 |
| 测试不便 | 无模块级测试目标，业务逻辑与 UI 耦合，难以对单个业务单元做独立验证 |

**提案（待评估）**：参考大型应用（Chrome / VS Code 等）的做法，把主进程按业务拆分为多个相对独立的应用程序，分别编码、编译、调试，最后用某种机制整合为一个大的应用。

---

## 2. 现状量化分析

结论先行：**当前构建慢的主因是"链接 + 静态库打包"，而不是"编译"，也不是代码架构本身。**

### 2.1 代码规模（第一方 src/）

| 层 | 文件数 | 行数 | 说明 |
| --- | --- | --- | --- |
| core | 89 | 12,399 | 设备、录制、回放、DBC、文件 I/O、插件系统 |
| models | 6 | 2,158 | Qt 数据模型 |
| ui | 68 | 21,695 | 全部界面组件 |
| utils | 6 | 399 | 工具函数 |
| **合计** | **170** | **36,693** | — |

第三方内嵌（third_party/，173 个文件）：dbcppp、spdlog、nlohmann_json、qcustomplot、concurrentqueue。

**超大文件 Top 6**（AI 编码上下文压力的直接来源）：

| 文件 | 行数 |
| --- | --- |
| ui/mainwindow.cpp | 3,067 |
| ui/graphicview.cpp | 2,681 |
| ui/traceview.cpp | 2,168 |
| ui/measurementsetupview.cpp | 1,337 |
| ui/panels/sidebarpanels.cpp | 1,329 |
| ui/markettab.cpp | 1,115 |

### 2.2 构建配置现状

- 工具链：MinGW-w64 GCC 13.1（Qt 官方 mingw1310_64）+ **GNU ld.exe**（bfd 链接器）+ Ninja，`-j8`
- 构建类型：**Debug（全量调试信息）**
- 已有优化：`openbus_core` / `openbus_ui` 两个静态库分层 + 两级 PCH（说明"按库拆分编译"已经做过一轮，但没解决链接）
- 产物：`openbus.exe` **172 MB**（Debug 调试信息占大头）
- 已有的"拆分先例"：`drivers/` 下 5 个驱动 DLL（slcan/zlg/peak/kvaser/candle，编译期各 111~155s，互不牵连）+ .opk 插件系统（见《插件系统方案》《驱动系统方案》）

### 2.3 实测构建耗时（build/.ninja_log，最近一次全量构建）

| 构建步骤 | 耗时 | 占比（总 15.6 min） |
| --- | --- | --- |
| **openbus.exe 最终链接（GNU ld）** | **778 s ≈ 13 min** | **83%** |
| libopenbus_core.a 静态库打包 | 513~527 s ≈ 9 min（与其他步骤并行） | 并行段 |
| libopenbus_ui.a 静态库打包 | 64 s | 并行段 |
| 单文件编译（最慢） | appconfig.cpp 86 s / sessionmanager.cpp 84 s / qcustomplot.cpp 127 s / mainwindow.cpp 37 s / settingsdialog.cpp 39 s | — |
| 全量构建端到端 | ≈ 15.6 min | 100% |

### 2.4 增量修改的真实代价（最痛的场景）

| 修改场景 | 需要重做的步骤 | 端到端等待 |
| --- | --- | --- |
| 改 1 个 core 文件（如 appconfig.cpp） | 编译 1 文件 + **重新打包 core.a（9 min）** + **全量重链（13 min）** | **≈ 23 min** |
| 改 1 个 ui 文件（如 mainwindow.cpp） | 编译 1 文件 + 重新打包 ui.a（1 min） + **全量重链（13 min）** | **≈ 14 min** |

> **瓶颈结论**：无论改 core 还是 ui，等待时间的 80% 以上都花在同一件事上 —— GNU ld 把 172 MB 的 Debug 调试信息重新链接进单个 exe。这是**工具链问题**，不是模块划分问题。先解决它，收益立竿见影且零架构风险。

## 3. 候选方案

### 方案 A：构建工具链优化（不改变架构，零风险）

不动任何代码，只动构建配置：

| 措施 | 作用 | 预期收益 |
| --- | --- | --- |
| 评估引入 **LLD 链接器**（`-fuse-ld=lld`）替代 GNU ld | lld 对大体积调试信息的链接常见 5~10 倍加速（需 PoC 实测） | 13 min → 1~3 min |
| **开发档 RelWithDebInfo 或 `-g1`（仅行号表）** | 调试信息量下降一个数量级，链接与打包随之变快 | 链接/打包同步缩短 |
| **thin archive**（`ar qcT`，CMake 改 `CMAKE_CXX_ARCHIVE_CREATE`） | 静态库打包不复制对象文件内容，core.a 的 9 min 基本归零 | 9 min → 秒级 |
| **ccache** 编译缓存 | 命中缓存的编译直接跳过（AI 反复试错同文件时收益极大） | 单文件 37~86 s → 0 |
| Windows Defender 排除 build/ 目录 | 消除杀毒实时扫描对 obj/exe 写入的放大（Windows 上常见 2~5 倍因素） | 全流程加速 |
| 保留 `Debug` 全信息档作为"需要深入调试时"的可选档位 | 平时用快档，偶尔用全档 | — |

**预期组合效果**：日常迭代（改 1 个 ui 文件）从 ≈14 min 降到 **1~2 min**；改 core 文件从 ≈23 min 降到 **2~3 min**。

### 方案 B：模块化单体 — 按业务拆 DLL（拆模块，不拆进程）

把现在的 `openbus_core` / `openbus_ui` 两个大静态库，进一步按业务拆成**动态库**，壳工程只做装配：

```
openbus.exe（薄壳：主窗口装配、生命周期）
├── openbus_data.dll      （core 公共底座：CanFrame / DbcManager / AppConfig / 设备抽象）
├── openbus_trace.dll     （Trace 视图 + 模型 + 过滤引擎）
├── openbus_graphic.dll   （Graphic 视图 + QCustomPlot 封装）
├── openbus_transceive.dll（发送 / 回放 / 录制）
├── openbus_market.dll    （插件市场）
└── drivers/*.dll         （已有，保持不变）
```

- **迭代收益**：改 Trace 业务 → 只重编 `openbus_trace.dll`（小库链接秒级），壳与其他 DLL 不动、不重链。
- **运行时仍是一个进程**：现有信号槽、单例、内存模型、主题系统全部照常工作，无 IPC。
- **工程先例**：Qt Creator（插件化单体）、OBS Studio；以及本项目**已有的 5 个驱动 DLL 和 .opk 插件系统** —— 技术路线已被本仓库验证过。
- **配套动作**：mainwindow.cpp（3067 行）按业务瘦身拆解；每个业务 DLL 可配独立测试目标（模块级单测成为可能）；AI 编码时按模块开任务，上下文边界清晰。
- **代价**：需要定义模块间接口（导出头 / 工厂注册），一次性搬迁成本约 1~2 周；DLL 边界要求头文件干净（反而倒逼架构改善）。

### 方案 C：多进程拆分 — 独立 EXE + 壳集成（本提案）

按业务拆成多个**独立进程**，"分别编码、编译、调试，最终整合成一个大的应用"。整合形态有两种：

- **C1：壳进程嵌入子应用窗口** —— 用 `QWindow::fromWinId` / Win32 `SetParent` 把子进程的 HWND 拼进主窗口，看起来像一个应用。
- **C2：各子应用独立顶层窗口 + 统一启动器** —— 不拼窗口，仅共享品牌与数据。

进程间通信候选：QtRemoteObjects（信号槽跨进程复制）、共享内存环形缓冲（高频 CAN 数据）、本地命名管道 / 套接字（控制命令）。

### 方案 D：混合分层（A + B 先行，C 局部使用）

工具链优化（A）立即做；业务按 B 拆 DLL；**只把真正需要隔离的"无头服务"进程化**（长时间运行、可崩溃重启、与 UI 无关的部分，例如：诊断 UDS 会话、BLF/ASC 转换作业、驱动宿主）。

## 4. 方案对比总表

| 维度 | A 工具链优化 | B 模块化单体(DLL) | C 多进程拆分 | D 混合 |
| --- | --- | --- | --- | --- |
| 日常迭代速度 | ★★★★★（1~2 min） | ★★★★（秒级编 DLL，无全量链） | ★★★★（各 EXE 独立编译） | ★★★★★ |
| 实施风险 | 极低（改构建脚本） | 中（接口定义 + 搬迁） | **高**（IPC + 窗口嵌入 + 状态复制） | 中 |
| 迁移成本 | 0.5~1 天 | 1~2 周 | **1~2 个月起**，且持续投入 | 1~2 周 + 局部 |
| 高频 CAN 数据吞吐 | 无影响 | 无影响（同进程） | **跨进程复制/共享内存，复杂**（CANoe 即此路线，商业级投入） | 仅隔离部分有 |
| UI 一致性（主题/快捷键/拖放） | 无影响 | 无影响 | **每进程一套 ThemeManager + IPC 同步；跨进程拖放/菜单/模态均要自制** | 主 UI 无影响 |
| 调试便利 | 无变化 | 改善（模块边界清晰） | **变差**：多进程 attach、状态分散、时序问题难复现 | 主链路不变差 |
| 测试便利 | 无变化 | **明显改善**（模块级测试目标） | 改善但测试编排变复杂（需拉起多进程） | 明显改善 |
| AI 编码效率 | 反馈回路缩短（最大杠杆） | **明显改善**（小模块 = 小上下文 + 快反馈） | 改善（仓库变小），但接口约束多 | 明显改善 |
| 崩溃隔离 | 无 | 无（同进程） | **有**（子进程崩溃不连坐） | 隔离部分有 |
| 内存/启动开销 | 无 | 略增（多个 DLL） | **每进程一份 Qt 运行时开销（数十 MB/进程）** | 小幅 |
| 与现有架构的兼容 | 完全兼容 | 高（driver DLL / 插件系统同路线） | 低（单例、信号槽、内存模型全要重构） | 高 |

## 5. 方案 C 关键技术难点逐项评估

C 并非不可行 —— CANoe、Chrome 都是成功先例 —— 但它们的做法与"直觉想象"有重要出入，逐项说明：

### 5.1 业界大型应用的真实拆分方式

- **Chrome**：多进程，但**没有任何一个 UI 窗口是"嵌入另一个进程的原生窗口"**。渲染进程把像素合成纹理交给浏览器进程合成显示 —— 是自研合成器，不是窗口拼合。
- **VS Code**：主窗口 UI 全部在单进程内；拆出去的是**无头进程**（扩展宿主、语言服务器、搜索服务）。
- **Qt Creator / OBS / Wireshark**：单进程插件化单体。
- **Vector CANoe**：测量内核与工具以多进程协作、报文经共享内存总线分发 —— 证明高频 CAN 数据跨进程**可行**，但那是商业级投入的成熟产品。

> 启示：**大型应用普遍"UI 一个进程 + 无头服务多进程"，极少做"多个带 UI 的进程窗口拼进一个主窗口"**（C1 形态）。C1 在 Windows 上的焦点、DPI 变化、弹出菜单定位、模态对话框、拖放、Z 序问题上都有长期维护成本。

### 5.2 高频 CAN 数据流跨进程

当前设备线程 → UI 的报文通路是**进程内无锁队列**（concurrentqueue），纳秒级搬运。拆进程后必须改为共享内存环形缓冲 + 序号协议，并处理慢消费者丢帧策略 —— 相当于在应用内重新实现一个小型"总线中间件"。可行（CANoe 路线），但工作量与出错面都大。

### 5.3 单例服务的进程化改造

`CanDeviceManager`、`DbcManager`、`AppConfig`、`SessionManager`、`ThemeManager`、`BookmarkManager` 等单例目前被所有 UI 直接调用。拆进程后每个单例都要变成"宿主进程内的服务 + 其他进程的代理对象"（QtRemoteObjects 或自研协议），是**全量接口改造**，牵动 170 个文件中的绝大多数。

### 5.4 调试与测试复杂度

- 多进程断点需要 attach 到正确进程；跨进程时序 bug（IPC 消息乱序、半更新状态）复现成本高。
- 自动化测试要编排"启动 N 个进程 + 等待就绪 + 收集结果"，比单进程测试目标复杂一个量级。
- 用户痛点里的"调试不便、测试不便"在 C 下**可能变得更严重**，而不是更好。

### 5.5 C 方案结论

- **可行性**：可行，属于重型架构投资，适合团队规模扩大、模块团队需要物理隔离、或需要崩溃隔离/独立升级的场景。
- **对当前四大痛点的针对性**：只有"编译链接慢"和"AI 上下文大"两项与 B 重叠受益；"调试不便""测试不便"反而可能恶化。
- **建议**：不做 C1（多 UI 进程窗口拼合）。若坚持 C 方向，先做 5.6 的 PoC 再决策。

### 5.6 若评审仍倾向 C：先行 PoC 清单（约 3 天）

1. 两个最小 Qt EXE + `QWindow::fromWinId` 嵌入，验证：DPI 切换、子窗口内弹出菜单/模态框、键盘焦点切换、拖放。
2. 共享内存环形缓冲搬运 10k 帧/秒 CAN 报文，测延迟与丢帧策略。
3. QtRemoteObjects 复制一个现有单例（如 DbcManager 的消息树），评估接口改造工作量。

三个实验全部通过再立项；任何一个不通过即回退到 D。

## 6. 四大痛点归因与方案匹配

| 痛点 | 根因 | 最优解 |
| --- | --- | --- |
| 编译链接慢 | GNU ld + 全量 Debug 调试信息 + 静态库全量重打包（**工具链问题**） | **A**（立竿见影），B 锦上添花 |
| AI 编码效率低 | 单文件过大 + 反馈回路过长 | **A（快反馈）+ B（模块上下文边界）**；与进程模型无关 |
| 调试不便 | 巨型类 / 巨型文件（mainwindow 3067 行） | **B**（拆模块拆文件）；多进程反而更难 |
| 测试不便 | 业务逻辑与 UI 耦合、无模块测试目标 | **B**（每 DLL 一个测试目标）；多进程测试编排更复杂 |

> 四个痛点没有一个是"必须拆进程"才能解决的；其中三个用 A+B 即可完全覆盖，且成本是 C 的十分之一。

## 7. 结论与建议

1. **立即执行 A（工具链优化）** —— 半天到一天工作量，迭代时间预计从 14~23 min 降到 1~3 min。这是当前收益/成本比最高、且无论如何都该做的一步（即使将来走 C 也需要）。
2. **中期执行 B（业务 DLL 化 + mainwindow 瘦身 + 模块测试目标）** —— 1~2 周，复用现有 driver DLL / 插件系统的成熟路线，同时解决 AI 上下文、调试、测试三个痛点。
3. **C 仅限"无头服务"局部采用（即 D）** —— 诊断会话、格式转换作业等长任务可进程化获得崩溃隔离；**不做多 UI 进程拼合（C1）**。
4. 本文档结论为工程评估意见，最终取舍请评审确定（评审要点：是否接受"C1 不做"的判断；是否需要先跑 5.6 的 PoC 再定 C）。

## 9. 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| lld 在 MinGW/Qt 组合下兼容性问题 | Phase 0 先 PoC，不通过则退回 `-g1` + thin archive + Defender 排除（仍有数倍收益） |
| DLL 拆分引入符号导出 / ABI 问题 | 全部走 CMake `AUTOMOC` + `generate_export_header`；接口先于搬迁冻结 |
| 模块间隐藏耦合导致搬迁反复 | Phase 2 先收敛接口，编译器强制边界（非公共头不可 include） |
| 期间主线功能开发受阻 | Phase 3 按业务逐个迁移，每步可编译可运行，不设长寿命分支 |
